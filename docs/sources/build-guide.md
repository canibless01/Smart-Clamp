PART 0 — FOUNDATION (Set This Up Before Writing a Single Page)
0.1 Stack, Decided
Frontend: Next.js (React) — server-rendered for public/marketing pages (SEO-critical: Home, Pricing, How It Works), client-rendered for everything behind login. No AWS Amplify — it would duplicate what Supabase already does.
Backend: Python/Flask — owns all business logic. Nothing that calculates, validates, or decides anything lives in Supabase or in the frontend.
Database: Supabase (PostgreSQL) — tables, Auth, Row-Level Security, Storage, and Realtime subscriptions only. Not used for Edge Functions or business logic.
0.1a The Master Flow — How Every Piece in This Document Actually Fits Together
Before the individual endpoints, the shape of the whole system in one pass — every specific function in this document is an implementation of one step below:
Device (clamp/meter/IR-Reader) → measures current/voltage or reads a meter      ↓ signs payload with its own device_hmac_key (Part 4.1.1)Flask Backend → verifies signature → stores as a usage_events row      ↓"Rule Engine" (not a single function — this is every one of the following, each triggered by that same incoming reading):   · Wallet balance check (relay-equipped devices)      → issue_command_token if 0 (Part 3.11c)   · Budget limit check (if set)                         → issue_command_token if hit (Part 3.11c)   · Schedule check (if set, on a timer not the reading) → issue_command_token at set time (Part 3.11b)   · Upstream drift comparison (Part 3.12, 4.2, 5.2)      → create_alert if mismatched      ↓Any relay command → attaches a CommandToken → device verifies independently before acting (Part 3.11)      ↓Alert dispatched (SMS + push) where a rule fires      ↓Dashboard reads usage_events + wallets + alerts in real time (Part 3.9, Supabase Realtime)
Nothing in this system trusts a single reading, or a single command, in isolation — this is the one sentence every individual security/verification decision in this document traces back to.
0.2 Architecture Boundary (Applies to Every Endpoint in This Document)
Next.js  ──HTTPS/JSON──▶  Flask API  ──psycopg2/SQLAlchemy──▶  Supabase/Postgres   ▲                                                                  │   └───────────── Supabase Auth (signup/login/token only) ◀──────────┘   └───────────── Supabase Realtime (live dashboard numbers only) ◀──┘
The frontend talks to Supabase directly only for (a) authentication and (b) real-time subscriptions to already-fetched data. Every write and every business calculation goes through Flask. This is the rule that prevents the schema/logic drift you’re worried about — there is exactly one place business logic can live, so there’s exactly one place to check when something behaves unexpectedly.
0.3 The Feature Flag System (Built Now, Enforced From the First Line of Code — Not Bolted On Later)
The problem this solves directly: a flag that exists in a database but that no code actually checks is not a feature flag — it’s a decoration. Every gated feature in this entire system, from day one, is wired through this exact mechanism. There is no other way a feature is ever hidden or shown.
Schema (add to Part 1’s schema):
CREATE TABLE feature_flags (  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),  key TEXT UNIQUE NOT NULL,                    -- e.g. 'basic_pro_load_signature', 'ir_reader_live_balance'  description TEXT,  enabled_globally BOOLEAN NOT NULL DEFAULT false,  enabled_for_tiers subscription_tier[],       -- e.g. ARRAY['basic_pro','pro']  enabled_for_building_ids UUID[],             -- for a pilot-area-specific rollout, PRD Section 12.6 Panel J  created_at TIMESTAMPTZ NOT NULL DEFAULT now());
Backend enforcement — every gated endpoint uses this decorator, no exceptions:

If the flag isn’t on, the endpoint returns 403 — the underlying feature is unreachable, not just unlinked from a menu. This is the difference between a real flag and a cosmetic one.
Frontend enforcement — the same flags, not re-decided independently: 1. On login (Part 3.2 below), the frontend calls GET /api/v1/feature-flags/active, which runs the exact same is_feature_enabled() logic server-side for the current user and returns the list of keys that are true for them. 2. This list is stored once (React Context or a small store), not re-derived by the frontend guessing at tier/rollout logic itself. 3. Every conditionally-shown button, panel, or page checks membership in this list before rendering:
{activeFlags.includes('basic_pro_load_signature') && <LoadSignatureWidget />}
The rule stated plainly: the frontend never independently decides who gets to see a feature. It only ever asks the backend “what am I allowed to see,” and renders accordingly. The backend’s 403 on the actual endpoint is the real security boundary; the frontend check is what makes the UI not show a dead button.

3.5 Device Pairing (Installer App — BLE Step, Then This Registration Call)
Physical Installation Safety Protocol (restored — this was dropped during an earlier edit and never made it into any version of the build spec): standard low-voltage electrical work practice, not a novel procedure. Insulated tools rated for the wire’s voltage class at every step; installer PPE (gloves, eye protection) worn throughout any clamp installation. Critically: a qualified electrician — not just the installer — handles the actual clamp closure on any wire that has not first been de-energized. The BLE-based configuration and diagnostic steps below can be done by a trained installer without an electrician present; the moment of physically closing a CT clamp around a live wire is the one step reserved for someone electrically qualified to do it safely. This distinction belongs in installer training material explicitly, not left implicit.
Frontend (Installer Portal, /portal/installer/pair-device): - The BLE configuration itself (assigning Wi-Fi/GSM credentials to the physical device) happens over Bluetooth, handled by native mobile BLE APIs, not this web spec — but the moment that device successfully connects to the internet for the first time, the installer’s app screen shows a “Registering…” spinner while it calls the endpoint below, then displays the returned key with a clear instruction: “Enter this key into the device now via [BLE tool] — it will not be shown again.”
Backend: POST /api/v1/devices/register — Auth: installer or internal_ops role. Request: { "role": "pole_gateway|pole_device|house_full|building_hub|transformer_monitor|ir_reader", "has_relay": true, "has_voltage_sensor": true, "room_id": "uuid|null", "building_id": "uuid|null", "pole_group_id": "uuid|null" }
def register_device(role, has_relay, has_voltage_sensor, room_id, building_id, pole_group_id, installer_id):    device_id = str(uuid.uuid4())    raw_key = secrets.token_hex(32)    encrypted_key = encrypt_at_rest(raw_key, DEVICE_HMAC_ENCRYPTION_KEY)  # reversible, NOT bcrypt/argon2    db.execute("""        INSERT INTO devices (id, role, has_relay, has_voltage_sensor, room_id, building_id,                              pole_group_id, device_hmac_key, installer_id, installed_at)        VALUES (%s,%s,%s,%s,%s,%s,%s,%s,%s, now())    """, (device_id, role, has_relay, has_voltage_sensor, room_id, building_id, pole_group_id, encrypted_key, installer_id))    if role == 'house_full' and room_id:        db.execute("INSERT INTO wallets (device_id, balance_units) VALUES (%s, 0)", (device_id,))    return {"device_id": device_id, "device_hmac_key_raw": raw_key}
Response: { "device_id": "uuid", "device_hmac_key_raw": "string — burn into firmware now, never shown again" }

def issue_command_token(device_id, command, issued_to, requires_step_up):    token_raw = secrets.token_hex(16)    key = decrypt_at_rest(get_device_hmac_key(device_id), DEVICE_HMAC_ENCRYPTION_KEY)    token_hash = hmac.new(key.encode(), token_raw.encode(), hashlib.sha256).hexdigest()    row = db.execute("""        INSERT INTO command_tokens (device_id, issued_to, command, token_hash, step_up_verified, expires_at)        VALUES (%s,%s,%s,%s,%s, now() + interval '2 minutes') RETURNING id    """, (device_id, issued_to, command, token_hash, not requires_step_up))    if requires_step_up:        send_sms_otp(issued_to)    else:        dispatch_to_device(device_id, command, token_raw)    return row

3.12 Tamper Detection (Backend-Only — No Frontend Page, Feeds the Alerts Feed Everywhere)

Threshold, stated explicitly: >8% drift sustained across 3 consecutive 5-minute checks (15 minutes total) — a single noisy reading never fires an alert; three in a row is the confirmation window.

4.1.1 Device Authentication (Different From User Authentication — Specified Now Since Phase 2 Is Where a Second Device Type First Needs It)
Devices don’t have passwords or JWTs. Every request from a device includes an X-Device-Signature header: an HMAC-SHA256 of the request body, computed with that device’s device_hmac_key (the same encrypted-at-rest secret from Part 1/Phase 1’s Command Token mechanism — one secret per device, used for both directions: the backend signs commands to the device, the device signs readings to the backend).
def verify_device_hmac_signature(device, payload, signature_header):    key = decrypt_at_rest(device['device_hmac_key'], DEVICE_HMAC_ENCRYPTION_KEY)    expected = hmac.new(key.encode(), json.dumps(payload, sort_keys=True).encode(), hashlib.sha256).hexdigest()    return hmac.compare_digest(expected, signature_header)

PRD Context for This Entire Phase (Section 08 — Unified Theft-Detection & Verification Framework, In Full)
Every quadrant runs on the same principle: any reading is only trusted if it’s cross-checked against a reading one level up.
08.1 Layer 1 — Hardware Tamper Detection. Clamp removed (current → zero while relay ON); relay bypassed (relay OFF but current > 0); clamp loosened (fluctuating readings); device offline (no heartbeat 24hrs). Applies everywhere, all phases.
08.2 Layer 2 — Relay vs. Current Correlation. Relay OFF + Current > 0 → bypassed. Relay ON + Current = 0 → clamp removed/wire cut. Relay ON + Current = normal → all good. Applies to any relay-equipped device.

08.5.5 Device & SIM Theft Tracking. Everything above protects against tampering with readings. This layer protects against someone stealing the device itself. Device location, without adding a GPS chip: each GSM-equipped device uses its existing GSM module’s cell-tower ID as a free location fingerprint, captured once at install as the baseline — any change afterward is itself the tamper signal, since these are fixed installations that never move under normal operation. SIM theft’s real fix removes the motive, not just the opportunity: IMEI-lock every SIM to its specific device via the M2M SIM platform, so a stolen SIM is worthless in any other device. Response to a detected tamper or theft is an urgent installer/ops-dispatch alert (visible on the Internal Ops Dashboard), never an automatic community-wide cutoff — Pole Devices keep working locally via ESP-NOW regardless of one device’s GSM status, so the real impact of a single stolen device is delayed data sync for that device alone, not lost service for its neighbors.

6.2 The Three-Tier Correlation Engine — Thresholds Get Tighter as Physical Distance Shrinks
Phase 1 introduced Pole-vs-House drift detection (8% threshold). Phase 2 added Clamp-vs-Meter (5%, tighter — both readings originate from the same physical point, so real disagreement is more likely miscalibration than legitimate variance). Phase 3 completes the chain at the top:

STS (Standard Transfer Specification) primarily governs the token format generated during a recharge — Phase 1’s recharge flow (Part 3.8) already produces a unit credit; STS compliance means that credit needs to be encoded as a proper STS token string for any customer-facing display/printout, once certification requires it. This doesn’t add a new endpoint — it changes what wallet_credit_units gets formatted into on the confirmation SMS/receipt. Flag this for whoever handles the actual STS certification to confirm the exact encoding library/standard before this ships — noted here so it isn’t discovered as a surprise late in Phase 3.

6.4 Deeper Anomaly Detection (New Layer, Distinct From Phase 1’s Threshold Checks)
Runs alongside, not instead of, the existing threshold-based drift detection (Part 3.12, Part 4.2, Part 5.2) — those stay exactly as they are, since they catch clear-cut mismatches cheaply and immediately. This adds a second, subtler layer for patterns a fixed percentage threshold can’t catch — e.g., a slow, gradual drift that never crosses 8% at any single check but is clearly abnormal over weeks.
def compute_anomaly_score(device_id):    """Runs nightly, not on every reading — this is a batch analysis, not real-time."""    recent_pattern = get_usage_pattern_vector(device_id, days=30)    historical_baseline = get_usage_pattern_vector(device_id, days=180, exclude_recent=30)    model = load_anomaly_detection_model()  # e.g. an isolation forest or a simple statistical                                              # z-score across pattern features — interface-first,                                              # same honesty note as 6.3 above    score = model.score(recent_pattern, baseline=historical_baseline)    db.execute(        "INSERT INTO anomaly_scores (device_id, anomaly_score, model_version) VALUES (%s,%s,%s)",        (device_id, score, CURRENT_MODEL_VERSION)    )    if score > 0.85:        create_alert(device_id=device_id, type='behavioral_anomaly', severity='warning',                     message=f"Unusual usage pattern detected (score: {score:.2f}) — review recommended, not an automatic tamper confirmation")
Important distinction from the Phase 1/2/3 drift alerts: this alert type is explicitly framed as “review recommended,” not “tamper confirmed” — a statistical anomaly is a prompt for a human (or the Ops Dashboard’s alert triage) to look closer, not an automatic accusation the way a clean threshold breach is. Conflating the two would make the softer signal carry the same weight as the harder one, which isn’t accurate.
